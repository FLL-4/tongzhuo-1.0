# 《在场》产品设计基线

> 用于后续功能开发、模块拆分和重构评审。本文描述产品契约，不等同于某个具体页面实现。

## 0. 当前代码功能（2026-08-12）

当前 SwiftUI Demo 在 Mac、iPhone 和 iPad 共用领域模型，已有功能如下：

- 单窗口主页、桌面/紧凑布局、导航、Toast 和单条在场建议。
- 今日 Todo 的新增、改名、删除和完成状态，最多 5 项。
- 专注、安静、休息、离开 4 种在场状态，以及计时的开始、暂停、继续和重置。
- 内置场景、环境声、雨效和场景工坊；场景图片已能随手动选择真实刷新。
- 好友照片、桌宠生成预览、重新生成、启用和清除，桌宠以独立前景图层渲染。
- 同桌房间的创建、任意非空邀请码加入、复制房间码和离开。创建后进入空房等待，加入对方房间时 Mock “阿禾”在线。
- 同桌专注前可选 `15/25/45/60` 分钟和 1 项未完成 Todo，开始时随机选场景并留在主页。
- 专注中可换场景且不重置会话与倒计时；计时结束或用户确认手动结束都生成一次活动结束事件。
- 两种结束方式都会生成建议：有同桌时引导留声，无同桌时建议休息；不自动完成 Todo。
- 留声机已支持录音权限、录制、试听、重录和本地保存；共同记忆页当前为静态 Demo。

当前尚未实现：账号与后端、WebSocket/跨设备同步、拍一拍的跨端送达、自动 AI 记忆卡生成与真实延迟送达。

## 1. 产品定位

《在场》是一款面向 Mac、iPhone 和 iPad 的共享陪伴空间。用户先把“今天要做的事”和想进入的状态放到桌面，再通过场景、桌宠和同桌关系进入一段可持续的活动。产品的核心不是让 AI 代替关系，而是让两个人更容易在各自生活里留下可回到的共同时刻。

产品有两个平行主线：

| 主线 | 解决的问题 | 核心结果 |
| --- | --- | --- |
| 同桌 | 两个人不在同一地点，也想一起开始、持续和结束一段活动 | 共同专注、低打扰互动、清晰的在场状态 |
| 留声机 | 活动结束后，重要感受和细节容易消失，想表达又不想打断对方 | 经过确认的记忆卡片、延迟送达、共同回忆 |

桌宠是两条主线共用的表达层，不单独承担聊天或情感诊断功能。

## 2. 核心用户闭环

```text
好友照片
  -> 卡通桌宠
  -> 今日 Todo
  -> 基础状态
  -> 场景主页
  -> 同桌/独处活动
  -> 活动结束
  -> 留声机记录
  -> AI 整理草稿
  -> 用户确认
  -> 记忆卡片与延迟送达
  -> 回忆系统
```

### 2.1 首次设置：桌宠

用户从好友档案中选择一张照片，生成卡通形象预览。MVP 只需要两个桌宠动作状态：`静止` 和 `移动`。桌宠作为独立前景图层叠加在场景背景上，不能写死进背景图。

生成流程必须允许：

- 选择照片、预览、重新生成、确认使用、移除。
- 明确提示照片只用于生成桌宠，提供删除入口。
- 失败时保留原照片选择，不丢失用户上下文。
- 生成结果保存为可替换资源，不能让 UI 依赖某个具体图片文件名。

桌宠的行为边界：

- 可以在场景前方移动或静止。
- 可以被最小化到桌面边缘。
- 最小化状态支持“拍一拍”。
- 不出现聊天气泡、人格化自言自语或代替用户发消息。

### 2.2 每日开始：Todo 与基础状态

用户先选择“今天放在桌上的事”，再选择一种基础状态。Todo 是当天活动的意图集合，不等同于专注计时器；计时器只是执行工具。

#### 基础状态的收敛原则

基础状态描述的是“这段时间准备以什么节奏和姿态生活”，不是具体地点，也不是一项任务。背景只负责表达环境、光线和节奏；人物、桌宠、Todo 和同桌信息全部以前景或 UI 图层叠加。这样可以避免为“在咖啡馆写作”“在家看论文”“在海边画画”分别制作一套业务状态。

经过收敛，MVP 固定四种基础状态：

| 状态 ID | 用户文案 | 背景方向 | 可绑定声音 |
| --- | --- | --- | --- |
| `focus` | 专注 | 桌面、书本、屏幕、稳定的室内光线 | 安静、雨声 |
| `make` | 创作 | 工作台、材料、纸张、局部暖光 | 安静、壁炉声 |
| `move` | 行动 | 训练空间、开阔地面、清爽的自然光 | 安静、环境声 |
| `roam` | 出走 | 林间道路、山野、车站或户外窗口 | 鸟鸣树林、安静 |

活动归类示例：

- `focus`：办公、学习、阅读、整理资料。
- `make`：写作、绘画、乐器、做手作、做饭。
- `move`：跑步、瑜伽、拉伸、健身、球类训练。
- `roam`：徒步、散步、骑行、逛展、短途出行。

“休息、听歌、发呆”不再单独占用一个基础状态，而是活动结束后的 `rest` 计时阶段；如果用户仍希望保留背景，则沿用当前活动的场景，不额外生成一套休息背景。这样首批背景只需要覆盖四类稳定构图，后续新增地点时仍复用状态模型。

状态定义应是数据驱动的 `BaseActivityState`，包含：背景资源、色彩主题、可用动态效果、声音预设、桌宠锚点和默认计时策略。一个活动只能绑定一个基础状态；中途改变状态应结束当前活动并新建下一段活动。新增状态不应要求改动首页布局或 `AppModel` 的分支判断。

### 2.3 主页渲染层

主页由四层组成：

1. `SceneBackground`：根据基础状态和天气选择 16:9 背景。
2. `AmbientEffects`：可开关的天气动态叠加层，例如雨。
3. `DeskPetLayer`：桌宠图像与状态机，只有静止/移动两个 MVP 状态。
4. `ProductControls`：同桌、留声机、Todo、声音和计时等控制。

场景资源与人物资源分离：

```text
scene/{stateID}/background.png
desk-pet/{profileID}/idle.png
desk-pet/{profileID}/moving.png
```

背景图始终只描述静态环境，人物和桌宠由独立图层控制；同桌加入或离开不会替换背景资源。

## 3. 主线一：同桌

### 3.1 目标

让双方在不被聊天打断的情况下共同开始、共同持续，并能用极低成本确认“我还在”。

### 3.2 核心流程

```text
本地 Mock 创建空房 / 任意非空邀请码加入阿禾的房间
  -> 选择 15/25/45/60 分钟
  -> 选择 1 项未完成今日 Todo
  -> 随机选择内置场景
  -> 关闭 Sheet 并留在主页
  -> 专注进行中
  -> 可手动换场景，不重置倒计时
  -> 计时器结束 / 用户确认手动结束
  -> 结束活动事件
  -> 有同桌时引导留声，无同桌时建议休息
```

### 3.3 在场建议

AI 在这里是后台协助器，不是陪伴角色。建议必须满足：

- 只在明确、可执行的情境出现。
- 同一时间最多一条。
- 有明确行动和关闭按钮。
- 执行或关闭后立即消失，依赖状态失效时自动消失。
- 不与内容相同的 Toast 同时出现。

MVP 触发：创建空房等待 5 分钟、重置计时器、专注自然结束、同桌加入 30 秒、暂停 5 分钟和每日 Todo 全部完成。建议不得推测对方心理、代发邀请、代发消息或自动保存共同记忆。

### 3.4 拍一拍

> 当前已实现本地 Mock 拍一拍，不包含真实跨端通信。

`拍一拍` 是唯一允许实时触达对方的互动。当前 Mock 中，只要加入对方房间并出现同桌即可发送，不要求自己已开始专注；创建的空房不可发送。它应是短暂、低噪音、可忽略的视觉反馈：桌宠轻微动作、短时亮起或一条轻量状态标记。

暂不加入：实时聊天、实时语音、连续表情轰炸、自动提醒对方回复。任何会改变对方状态或发送内容的动作都必须显式确认。

## 4. 主线二：留声机

### 4.1 目标

把活动中的细节保存下来，让表达可以脱离即时聊天的压力，在更合适的时机抵达对方。

### 4.2 输入

用户可以提交：

- 文字：心情、见闻、事件记忆点。
- 语音：一段原声留言，可选择是否附在卡片上。
- 活动上下文：基础状态、Todo、活动时长、发生时间。

### 4.3 AI 整理与创作

AI 的职责分为三步，每一步都产出可审查结果：

1. `MemoryDrafting`：从文字/语音转录中提取标题、时间、地点、心情、事件和关键词。
2. `CardPromptCompiling`：把结构化草稿编译为固定风格的图像/动图 Prompt。
3. `CardMetadataSuggesting`：建议卡片标签、BGM 氛围和送达时间。

AI 不得改变事实、补写未提及的人物关系或替用户向对方表达情绪。所有文案、图像、BGM 和送达时间都要先展示草稿，用户确认后才能保存或发送。

### 4.4 记忆卡片

记忆卡片是留声机的主要产物，形态可以借鉴集换式卡牌、角色卡和酒卡，但视觉必须服从《在场》的温暖像素风。

建议固定字段：

```swift
struct MemoryCardDraft {
    let id: UUID
    let sourceActivityID: UUID?
    var title: String
    var mood: MemoryMood
    var observation: String
    var keyMoment: String
    var imageAsset: AssetReference?
    var animationAsset: AssetReference?
    var musicAsset: AssetReference?
    var voiceNote: VoiceNoteReference?
    var delivery: DeliveryPlan
    var reviewState: MemoryCardReviewState
    var deliveryState: MemoryCardDeliveryState
}
```

建议分开表达两条生命周期：

```swift
enum MemoryCardReviewState: Codable, Equatable {
    case draft
    case generating
    case ready
    case confirmed
    case archived
    case failed(reason: String)
}

enum MemoryCardDeliveryState: Codable, Equatable {
    case notScheduled
    case scheduled
    case delivered
    case opened
    case failed(reason: String)
}
```

`failed` 必须携带可展示的重试原因；用户点击“重试”后回到 `generating`，未回到 `ready` 之前不能进入 `confirmed` 或送达。发送者的卡片在 `delivered` 后仍然可以保持未读，收件人手动打开副本后才进入 `opened`。不要用 `isGenerated`、`isSent`、`isOpened` 等多个布尔值表达这些状态。

### 4.5 延迟送达

延迟送达不是“AI 猜测对方什么时候需要安慰”，而是用户选择一个明确策略。创建者确认后，卡片先进入待送达状态；送达不要求对方提前授权，对方收到后自行决定什么时候打开：

- 活动结束后送达。
- 对方下一次结束专注后送达。
- 指定日期/时间送达。
- 仅保存到共同回忆，不送达。

发送前显示收件人、内容、附件、送达时间和撤回规则。对方收到的是不可共同编辑的副本。送达失败要保留在发件人的待发送状态，不重复发送；用户可以点击“重试”，在生成内容未完成时不能送达。送达后不自动打开，收件人通过自己的未读入口手动查看。

### 4.6 每日留声机触发

每日 Todo 全部完成时，触发“今日留声机”入口。它与单次活动结束是两个不同事件：

- `activityEnded`：计时器结束或用户手动结束一段活动，提供立即记录入口。
- `dailyTodoCompleted`：当天全部 Todo 完成，提供一次总结式记录入口。

两者可以在同一天同时发生，但不能复用同一个布尔状态；入口去重由事件 ID 和当天日期负责。

建议把结束事件固定为可持久化的领域对象：

```swift
enum ActivityEndReason: Codable, Equatable {
    case timerCompleted
    case manuallyEnded
}

struct ActivityEndedEvent: Codable, Identifiable {
    let id: UUID
    let activityID: UUID
    let reason: ActivityEndReason
    let endedAt: Date
}

struct DailyTodoCompletedEvent: Codable, Identifiable {
    let id: UUID
    let todoDay: String // YYYY-MM-DD in the user's calendar
    let completedAt: Date
}
```

这两个事件都可以打开留声机，但内容上下文不同：活动结束偏向“这一段发生了什么”，每日完成偏向“今天整体留下什么”。

## 5. 回忆系统

回忆是双方确认过的长期内容集合，不是自动生成的时间线。每条回忆至少记录：创建者、参与者、来源活动、确认时间、可见范围、资源引用和删除状态。

MVP 只做：

- 已确认卡片列表。
- 按时间和基础状态筛选。
- 查看图像、语音和 BGM。
- 删除自己的草稿或已保存卡片。

后续再考虑共同编辑、地点地图、年度回顾和跨设备同步。

## 6. 建议的模块边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `ActivityStateCatalog` | 基础状态、默认场景、声音和效果契约 | 具体页面布局 |
| `SceneRenderer` | 背景、效果、桌宠图层合成 | 同桌房间业务 |
| `DeskPet` | 照片、生成、启用、静止/移动状态 | 聊天和记忆整理 |
| `DeskRoom` | 房间、同桌、专注、拍一拍 | AI 文案生成 |
| `PresenceSuggestion` | 建议状态、触发、执行、关闭 | 长期设置页 |
| `VoiceRecorder` | 录音、权限、播放和资源引用 | AI 转录规则 |
| `Memory` | 草稿、卡片、送达、回忆归档 | 场景渲染 |
| `TextModelClient` | OpenAI-compatible 文本请求 | 业务决策和自动发送 |
| `ImageGenerationClient` | 图像/动图生成请求 | 用户确认和卡片生命周期 |

页面层只组合这些模块的状态，不直接拼装网络请求或修改另一位用户的数据。

## 7. MVP 取舍

### 本阶段必须完成

- 四种基础状态和主页背景切换。
- 好友照片生成桌宠的 Mock 流程。
- 桌宠静止/移动，以及最小化后的拍一拍 Mock 反馈。
- 同桌房间、专注计时和六种在场建议。
- 留声机文字/语音入口、AI 整理 Mock、记忆卡片预览。
- 延迟送达策略的本地状态机，不接真实推送也不自动发送。

### 本阶段明确不做

- 实时聊天和实时语音通话。
- AI 独立人格、情绪诊断、关系分析。
- AI 自动给对方发消息或邀请。
- 真实图像/动图生产链路和复杂角色动画。
- 未经确认的共同记忆保存。

## 8. 已确认的产品规则

以下规则已作为当前产品契约：

1. 每段活动的结束条件只有计时器结束和用户手动结束两种。
2. 每日 Todo 全部完成时，触发每日留声机入口。
3. 一段活动只能绑定一个基础状态；切换状态意味着结束当前活动并开始下一段。
4. 当前 Mock 中，加入对方房间后即可拍一拍；真实在线规则留待联机阶段定义。
5. 记忆卡片由发送者创建，对方收到不可共同编辑的副本。
6. 桌宠、原始语音、转写文本和卡片资源的保存期限一致，具体期限待隐私策略确定。
7. 延迟送达不需要对方预先授权；送达后由对方手动打开。
8. 图像或动图生成失败时，卡片停留在未完成状态，使用明确的“重试”按钮；未完成内容不可送达。
9. 暂不考虑回忆导出为图片或视频。

## 9. 待补充的产品问题

剩余问题主要集中在隐私、送达和资源策略：

1. 好友照片、桌宠、原始语音、转写文本和卡片资源的具体保存期限，以及删除是否立即影响已收到的副本。
2. BGM 使用本地素材、内置循环，还是未来接入版权音乐服务。
3. “对方下一次结束专注后送达”在对方长期不专注时是否允许创建者修改或取消。
4. 生成失败时是否允许只保存文字和语音版本，作为不含图像的备用卡片。

## 10. 重构验收原则

- 新增基础状态只需新增目录和数据定义，不改动主页面分支。
- UI 不直接持有 API Key，不在日志、Toast 或分析事件中输出密钥。
- 影响另一位用户的动作必须经过明确确认，并能追踪发送状态。
- 业务状态优先使用枚举和单一生命周期，避免相互矛盾的布尔字段。
- 每个网络客户端都有协议边界和 Mock 实现，单元测试不依赖真实网络。
- Mac、iOS、iPadOS 共用领域模型；平台差异留在 `Platform` 和 SwiftUI 适配层。
